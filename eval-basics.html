Evals basics

An eval is a repeatable test for software whose answers change every time. This article explains what that means, the two kinds of eval, and the habit that makes the rest work.

In one line: you cannot test AI output with a fixed expected answer. Instead, look at real outputs, name the ways they go wrong, and score each failure with a check you can repeat.

Why normal tests don't work here

Ordinary software is deterministic. Give a function the same input and you get the same output, so a unit test that compares against an exact value is enough.

An LLM is different. Ask the same question twice and you may get two different answers, and both can be fine. An exact-string check fails good answers and passes bad ones that happen to match. What you need is a judgement against criteria, repeated across many examples.

What an eval is made of

Every eval has the same three parts, whatever tool you use:

  1. A dataset of inputs. Real or realistic things users will ask. Start with 20 to 50, not 5,000.
  2. The output under test. What your product, prompt or model produced for each input. Keep the full trace if you can: the prompt, retrieved documents, tool calls and the final answer.
  3. A scorer. Something that returns a verdict for each output. It can be code (does the JSON parse?), a model acting as a judge (does the answer invent a policy?), or a person.

Two kinds of eval

Model evals

Compare models with a shared, public test set, such as a published benchmark. They help you shortlist which model to try first. They say little about your product.

Product evals

Test your own product on your own inputs, with criteria that match your users. This is the one that tells you whether the thing works, and the one this path is about.

Start with error analysis, not with a metric

The most common mistake is to pick a score (helpfulness out of 5, say) before you know what goes wrong. Scores like that hide the problems and drift over time.

The method that works, as taught by Hamel Husain and Shreya Shankar, goes like this:

  1. 1Collect real traces.Use real or realistic inputs and record what the system did, not only the final answer.
  2. 2Read them and note the first thing that went wrong.One short note per trace, such as "invented a refund policy" or "ignored the user's postcode".
  3. 3Group the notes into failure modes.Cluster similar notes into named categories. Count them. The biggest category is where to start.
  4. 4Write one eval per failure mode you care about.Next article: how to do that well with rubrics.

Reading 30 real outputs by hand usually teaches you more than a week of picking metrics. Do this before you buy any tool.

The eval loop

Evals are not a one-off. They run as a cycle:

Look at real outputs → name the failures → write an eval for each
      ↑                                              ↓
Change the prompt, tools or context  ←  Run evals, see what breaks

Each time you change the product, run the same evals again. A score that goes down is the signal to look at the traces, not to argue with the score.

Key terms

  • Trace: the full record of one run: inputs, prompts, retrieved context, tool calls and output.
  • Failure mode: a named, repeatable way the output goes wrong.
  • Ground truth / reference answer: an answer a human has agreed is correct, used to check a scorer.
  • Online eval: scoring real production traffic, not a fixed test set.
