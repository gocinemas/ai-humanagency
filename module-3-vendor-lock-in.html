Module 3: Vendor Lock-In Traps

How small early decisions become permanent. Why switching models costs millions. How to build a portable AI stack.

The Lock-In Problem

You choose Claude. You build your entire system around Claude's API, prompts, and behavior. Six months later, GPT-5 comes out and is 10x better. Can you switch?

Probably not. You've created invisible coupling that makes switching expensive and risky.

Three Types of Lock-In

1. Embedding Lock-In

You use Claude to generate embeddings for semantic search (RAG). You've embedded 10 million documents in Claude's embedding space.

Now you want to switch to OpenAI embeddings. Problem: OpenAI's embedding space is different. Your 10 million embeddings are useless. You need to:

  • Re-embed all 10M documents with the new model
  • Retrain any vector indices
  • Test that search quality doesn't degrade
Cost Example: Re-embedding 10M documents @ £0.02 per 1M tokens = £200. But it's the operational risk: if search breaks during cutover, your product is down for hours.

2. Prompt Lock-In

Your prompt works perfectly with Claude because it handles ambiguity gracefully. When you move to GPT-4, the same prompt produces different outputs:

Claude Prompt: "Categorize this receipt" ↓ Outputs: "Restaurant" Same Prompt + GPT-4: ↓ Outputs: "Food & Dining - Restaurant"

Now your system expects "Restaurant" but gets "Food & Dining - Restaurant". Your downstream code breaks.

Reality: Each model has quirks. Your prompts are tuned to those quirks. Switching means re-tuning all your prompts.

3. Model Behavior Lock-In

You've built features that depend on Claude's specific capabilities:

  • Claude is great at long-form summarization
  • Claude handles code better than GPT-3.5
  • Claude is more consistent on reasoning tasks

If you switch to a model that's worse at summarization, your feature degrades. You have to rebuild the feature differently.

Real Example: SaaS Company (2024)

Built a document summarization feature with OpenAI's GPT-4. Two years in, GPT-5 is released and costs 50% less.

Expected savings: £500k/year.

Actual outcome: GPT-5 summaries are shorter, less detailed. Customers complained. Took 3 months to rebuild the feature with GPT-5-specific prompting. Cost: £200k in engineering time.

Savings: £300k. Worth the switch, but not the expected £500k.

Why This Matters

Model leaders change. In 2023, GPT-3.5 was the go-to. In 2024, Claude took over. In 2025, Gemini got good. In 2026, who knows?

If you're locked in to one vendor, you:

  • Can't upgrade when a better model comes out
  • Overpay when the market shifts (no price pressure)
  • Can't hedge risk (what if that vendor has an outage?)
  • Are at the vendor's mercy for pricing
Real Metric (2026): Companies that switched models mid-project spent 3-6 months on the switch. Cost: £200k-500k in engineering time, plus product downtime.

How to Avoid Lock-In

1. Abstraction Layer

Don't call the API directly. Create an abstraction layer:

// Bad: Direct API call response = openai.ChatCompletion.create( model="gpt-4", messages=[{"role": "user", "content": prompt}] ) // Good: Abstraction response = llm.complete(prompt, config="summarization") // Internally: routes to Claude, GPT-4, or Gemini

Cost: 1-2 weeks of work. Payoff: Can switch models in days instead of months.

2. Standardized Prompts

Don't write model-specific prompts. Write prompts that work across models:

  • Use simple, explicit language
  • Provide examples (in-context learning works across models)
  • Avoid model-specific syntax

3. Structured Output

Force output into JSON schema, not free-form text. Validate against the schema. If GPT-4 outputs different field names than Claude, your validator catches it early.

4. Test Against Multiple Models

Before locking in to production, test on 2-3 models:

  • Claude (best on reasoning)
  • GPT-4 (most popular)
  • Gemini or open-source (cost control)

See which fits your use case. If two work equally well, you haven't locked in.

5. Open-Source Fallback

Keep a Llama 2 or Mistral version running. If proprietary pricing explodes, you have a fallback (with quality tradeoffs, but no lock-in).

Final Insight: Lock-in happens silently. You're not trapped until you try to switch. By then, it's expensive. Build portability from day one.

Your Lock-In Prevention Checklist

  • Build an abstraction layer between your code and API calls
  • Write model-agnostic prompts (not model-specific)
  • Use structured output (JSON validation)
  • Test against 2-3 models before production
  • Plan re-embedding costs if you use embeddings
  • Monitor if better models come out (quarterly)
  • Keep documentation on what would break if you switched
